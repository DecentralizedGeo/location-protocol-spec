## Direction findings (options for the maintainer, not ranked against bugs)

- **D1 — Ship the promised machine-readable registries.** `location-types.md:22` says "A formal registry is in development" with a designed naming convention (`<namespace>.<type>.v<major>`), and `composable-fields.md:192` promises "a static registry file, likely in a JSON format" for extensions. Neither exists in the repo. A `registry/location-types.json` (id, description, per-type schema `$ref`, status) would make the schema's `location_type` enum generated rather than hand-maintained, and gives Plan 001's residual looseness (untyped `wkt`/`address` strings) a home. Coarse effort: M–L.
- **D2 — Versioned, immutable schema publishing.** `schemas.md`'s validation procedure step 1 instructs loading the schema matching `lp_version`, but the repo publishes exactly one schema whose `$id` tracks the mutable `main` branch. Publishing `json-schema/1.0.0/schema.json` (or git tags + release URLs) and freezing `$id` per version makes the "select schema by lp_version" instruction executable and protects already-signed payloads from schema drift. Coarse effort: M.
- **D3 — Golden test vectors for the encoding pipeline.** `encoding.md` exists to guarantee byte-for-byte reproducibility, and the repo already hand-maintains one worked example (payload → CBOR hex → base64url → SHA-256, kept consistent only by care). A `test-vectors/` directory consumed by Plan 005's CI — and offered to SDK implementers (AstralSDK is named in `composable-fields.md:194`) — is the cheapest interop insurance this protocol can buy. Coarse effort: S–M after Plans 003/005.
